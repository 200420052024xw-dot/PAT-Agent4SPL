PAT-Agent: Autoformalization for Model Checking
ASE 2025（IEEE/ACM International Conference on Automated Software Engineering），Zuo et al., NUS。

一句话描述
PAT-Agent 让 LLM 先把自然语言描述拆成结构化建模计划、再翻译成 CSP# 形式模型,交给 PAT 模型检验器验证,并用返回的反例驱动定点修复、迭代至全部断言符合用户预期,在 40 个系统上达到 100% 验证通过率。

核心问题与核心思想
1.1 困境：为什么不能直接让 LLM 写 CSP#
把 NL 直接喂给最强单模型让它吐 CSP#，会发生什么？本文 Table III 给了数字：直接生成（o3 / Claude / R1，且已配同样的 RAG + 语法文档）在 40 个系统上的 full-pass rate 只有 37.5%–52.5%，最强的单模型（Claude）仍有 25% 的系统连编译都过不了。失败集中在：条件处理不全、需求误读、复杂系统的抽象错误。换句话说——LLM 有生成能力，但没有"逼自己对"的机制。而形式化的价值恰恰在于"对不对是可判定的"，这个判定器却没被用进生成回路。
1.2 思想：把可判定性变成一个收敛回路
一句话解法：不做端到端 NL→code，而是 plan（可解释中间表示）→ gen（结构化代码）→ verify（PAT 判定）→ repair（反例驱动的定点修改），让 LLM 的随机生成被 model checker 的反馈闭环收敛到"全部断言匹配期望"。
三点机制：
异构分工：Planning LLM（o3，即 o3-mini-2025-01-31）负责结构化抽取（常量/变量/动作/guard）并产出逐行 NL 计划；Code-Gen LLM（Claude，即 claude-3-7-sonnet-20250219）负责把计划翻成 CSP#。
判定器进回路：PAT 对每条 φᵢ 给 VALID/INVALID，与用户预设 oᵢ 比对，得 MATCH/MISMATCH 向量 + 反例 trace。
反例驱动修复：不重跑 planning，只把 trace + 属性类型相关的修复方向（safety 收紧 guard / liveness 放松）拼成增量 prompt 喂回 Code-Gen，最多 Kmax=5 轮。

Running Example
故事是这样的。 你想给一辆车建个模型,验证它安全不安全。车里有四样东西在互相影响:人在哪（车外/车内）、钥匙在哪、门是锁着还是开着、发动机什么状态。你不需要懂任何形式化语言,只要用大白话把车怎么运作描述一遍就行,比如描述发动机那段大意是:"发动机能开能关,车能起步能停,开起来油会慢慢耗掉,没油了可以加油。"
第一步,系统先把你的话拆成零件。 规划模型读你这段描述,自动列出:有哪些"状态变量"（车在动还是停、油量多少、发动机开没开、人在不在车里）、每个变量能取什么值、初始值是什么。这一步的产出是几张结构化的表,你能看懂、也能直接改——不需要看代码。
第二步,系统补上你没说的常识。 这里是有意思的地方。你说"车能起步",但你没说起步需要什么条件。系统会自己推断:要起步,得发动机是开的、车当前是停的、油量大于零、而且人得在车里。这些你觉得理所当然、懒得写的前提,它替你补齐了。
第三步,翻成代码。 上面那句常识,一对一翻成一行形式化代码,长这样:
[发动机==开 && 车==停 && 油>0 && 人==车内] 起步{车=行驶;} -> 发动机进程()
方括号里是"必须满足的条件",后面是"那就可以起步,车变成行驶状态"。
第四步,提要求并检查。 你提三条要求,而且要说明你期望的答案:
1.这车不会卡死(死机) → 期望"成立"
2.不会出现"钥匙锁在车里、人在车外"这种尴尬 → 期望"不成立"(即这种情况不该发生)
3.不会出现"车在开、驾驶座上没人" → 期望"不成立"
然后 PAT 这个检查工具去穷举车所有可能的行为。前两条通过了。第三条出事了:工具说"车在开但没人"这种情况真的能发生——而你期望它不该发生。
第五步,工具给你看它是怎么做到的。 这是形式化方法最值钱的地方——它不只说"有问题",它给你一条完整的作案路径:
人走近车 → 拿起钥匙 → 开锁 → 开门 → 人进车 → 打着火 → 人下车了 → 车起步
看到问题了吗?人下车之后,车居然还能起步。因为第二步补条件时,漏掉了"起步时人必须在车里"这一条——或者说,补了,但发动机打着之后没人再检查人还在不在。
第六步,定点修。 系统看这条路径,注意到出问题的最后一个动作是"起步",就判断毛病八成出在"起步"这个动作的条件上。又因为违反的是一条安全要求(坏事不该发生),修的方向就是把条件收紧——给"起步"补上"人必须在车里"的检查。改完再验一遍,三条要求全过。
为什么这个例子选得好。 它同时展示了三件事:LLM 能替你补常识(第二步)、形式化工具能揪出你想不到的漏洞(第四步)、反例能精确指出该改哪一行(第五、六步)。而且"车在开但驾驶座没人"这个 bug,普通测试很难碰上——你得恰好试到"打着火之后再下车"这个顺序。穷举检查不会漏。
不过按教程 §2.4 那条批判,这个例子也暴露了方法的软肋:它只保证你提的那三条要求过了。"没系安全带能不能开"、"没油了会不会卡死"——你没提,就没人查。修复环是朝着你给的答案收敛的,不是朝着"这车真的安全"收敛的。
