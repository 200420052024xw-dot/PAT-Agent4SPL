# Controller_IR → CSP#：语义缺口与改进分析

分析日期：2026-10-10。

本文依据当前 `src/` 实现、`inputs/Controller_IR/Internal-Comms-IR.json`、仓库内转换方案和 PAT 官方文档，分析转换过程中尚未充分表达的语义。结论来自代码和输入的静态核对；本文没有为这些问题重新运行 PAT，也没有将示意路径当作已执行的反例。

## 一、核心判断

**当前验证范围仅覆盖流程设计的合理性，暂不考虑环境交互。** 用户、工具等外部行为可作为动作的有限返回结果进行抽象，不要求建模真实请求、等待、响应、超时、取消或并发同步协议，也不验证外部系统是否按预期运行。

当前重点是：分支条件是否完整且一致、流程是否可达、是否存在无路可走的状态或不合理循环、状态更新是否正确，以及完成与失败去向是否符合设计。动作成功／失败及有限返回值抽象在这一范围内可以成立。

目前实现主要保留了流程连接关系和槽位判断，但尚未充分保留以下信息：

- 分支属于条件路由、控制器内部选择，还是抽象结果的非确定选择。
- 下一步依据什么决定：结构化 Guard、自然语言说明、抽象后的反馈类别或历史状态。
- 数据是否仍然有效：证据是否对应当前需求，反馈是否对应当前展示版本。

因此，生成模型能够被 PAT 检查，不等于检查结论已经可靠地对应原 Controller_IR 的流程设计要求。本文后续所述缺口均应按上述范围判断。

需要区分三类不足：

1. **Controller_IR 表达不足**：运行所需的语义仅存在于自然语言中，或没有明确执行约定。
2. **转换器表达不足**：已有语义未进入 CSP_IR，或被统一转换成了不同含义的行为。
3. **验证依据不足**：没有说明抽象保留哪些性质，以及检查结果能支持多强的结论。

## 二、选择语义：不能把所有分支统一为 `[]`

### 1. 当前实现

`src/model.py` 中的 `Process` 和 `Edge` 没有记录选择类型。`src/conversion/renderer.py` 的 `_render_process()` 将同一控制位置的所有出边统一用 `[]` 连接。

这覆盖了含义不同的情况：

- 动作成功与失败。
- 未知枚举返回不同值。
- 多个 Guard 成立时转向不同 Stage。
- policy 的不同结果。

当前转换方案还明确约定：未知枚举成功写回使用 `[]` 展开全部合法枚举值。这个约定实现了结果枚举，但没有说明这种选择由谁决定。

### 2. PAT 版本差异

本次核对的仓库文件 `PAT.Console/Process-Analysis-Toolkit/Modules/CSP/PAT.Module.CSP.dll` 的版本为 **3.5.1.20167**。

PAT 3.5 官方文档区分：

| 运算符 | 含义 |
|---|---|
| `P [] Q` | 一般选择，由先发生的事件解决选择 |
| `P [*] Q` | 外部选择，由可见事件解决选择 |
| `P <> Q` | 内部非确定选择 |

当两边首事件均可见时，前两者等价。旧版文档中的记法不同，分析时应以使用版本对应的说明为准。[PAT 官方进程定义](https://www.comp.nus.edu.sg/~pat/OnlineHelp/scr/3.1%20CSP%20Module/3.1.1.2%20Process%20Definitions.htm)

### 3. 应当区分的选择来源

| 分支来源 | 需要表达的行为 |
|---|---|
| 抽象反馈为接受、修改或提问 | 根据动作返回的有限类别路由，无需建模真实用户交互 |
| 黑盒动作返回某个合法结果 | 用非确定结果覆盖流程需要考虑的返回情况 |
| 根据已知槽位选择下一站 | 条件路由，并明确是否有优先级 |
| 控制器主动选择策略 | 控制器内部决策 |
| 抽象无法区分具体情况 | 抽象引入的非确定性 |

选择类型应属于具体的选择位置，而不只是整个 Stage。一个 Stage 内部可能先产生抽象动作结果，再根据结果进行条件路由；这两处选择的含义不同。当前不因存在用户或工具就要求采用外部选择或建立环境进程，运算符应依据流程抽象需要决定。

### 4. 不能直接全部替换为 `<>`

考虑以下示意：

```csp
P() = [false] a -> Skip [] [true] b -> Skip;
Q() = ([false] a -> Skip) <> ([true] b -> Skip);
```

一般选择可以执行成立的 `b` 分支；内部选择则可能先承诺进入 Guard 为假的分支，随后阻塞。因此，替换运算符之前，必须明确内部选择是在合法候选之间进行，还是先选择再等待条件。

当前模型只有单个顺序控制器，分支首事件均可见，部分内部选择与一般选择在观察到的有限事件轨迹上可能相同。确定存在的是选择语义的表达缺口，不能仅据此断言所有现有验证结果均错误。

## 三、出边说明中的业务条件没有进入 Guard

### 1. 具体例子：审阅后完成

输入中的 `present_and_review → completed` 出边说明要求：

> 用户明确接受刚刚展示的这一版，且没有同时要求修改或提问。

但实际 Guard 只检查：

```text
doActivity.execution_status == success
并且 draft 非空
```

`src/conversion/compiler.py` 的 `_compile_outgoing()` 直接编译 Guard，没有将出边 description 中的“明确接受”变成额外约束。

按当前生成规则，展示动作成功且草稿非空时，完成分支即可执行；模型没有要求反馈表达接受。这是代码层面允许的行为，本文未将其作为已运行 PAT 得到的反例。

同一个 Stage 中，“修改需求”“反馈含糊”“提出问题”等出边使用 `guard: true`。原本依赖不同用户意图的分支，在模型中成为同时可选分支。

### 2. 问题归属

- **IR 层**：关键决策依据只存在于自然语言说明，没有结构化条件。
- **转换层**：没有报告说明中的业务约束未被 Guard 覆盖，仍可输出模型。

如果实际执行器本来就要求 LLM 综合 description 选择出边，那么转换器应表达该决策过程，或明确声明这一部分尚未建模。单纯更换 `[]` 或 `<>` 无法补回缺失的决策依据。

建议区分“精确保留显式 Guard”与“根据自然语言补充执行语义”两种转换依据，并记录补充规则的来源和不确定性。

这里检查的是“完成分支是否以接受为前提”，而非真实用户是否回复、回复如何到达或意图识别是否准确。可以把接受、修改、提问、含糊等作为有限返回类别，检查各类结果的流程去向。

## 四、动作抽象的当前边界：保留结果与流程影响

`_compile_step()` 大致将每个动作编译为：

```text
动作位置 → 成功并写回
        或失败
```

在仅检查流程设计合理性的范围内，这种抽象本身不属于缺陷。真实请求、等待、响应及 participant 环境进程暂不纳入模型；`wait_for_reply` 没有展开成交互协议，也不作为当前改进项。

需要检查的是动作结果对流程的影响是否保留完整：

- 成功与失败是否具有符合设计的后继。
- 不同合法返回值是否会影响下一步，影响路由的类别是否被区分。
- 成功或失败后的槽位写回、清空和保留是否符合约定。
- 进入动作所在 Stage 时，必要的流程前提是否成立。

例如，若接受和修改需要走不同出边，仅保留 `success` 就过粗；应补充有限反馈类别。若某动作所有成功结果都具有相同的后续流程和状态影响，则无需展开其内部实现或环境交互。

## 五、Stage 生命周期顺序缺少明确执行契约

当前 `_next()` 固定执行：

```text
entry → doActivity → exit → policy → transitions
```

这意味着先执行 exit，再判断下一站。

如果 Controller_IR 采用“确定迁移后才退出当前状态”的状态机含义，这一顺序可能造成：

- 没有可用迁移时，exit 已经产生副作用。
- exit 的写回改变本次出边的可用性。
- 不离开状态的内部行为被解释为退出后重新进入。

不能仅根据 `entry/doActivity/exit` 的名称推定它遵循某种状态机标准。需要先明确 Controller_IR 自身的执行契约，再决定当前顺序是否正确。

还应明确自循环是否重新执行 entry、失败是否执行 exit，以及 policy 的触发位置和多个 policy 的先后关系。当前 policy 被编译为固定位置的顺序步骤，这只是特定执行假设。

## 六、抽象保留了非空性，却没有充分保留来源与版本关系

实际 IR 要求：

- 修改需求后不得沿用旧证据。
- 新草稿不能复用旧反馈作为确认。
- 接受必须针对刚刚展示的版本。

如果新旧草稿均抽象为“非空”，新旧反馈也均抽象为“非空”，以下情况就可能无法区分：

```text
旧草稿 + 旧确认
新草稿 + 旧确认
新草稿 + 新确认
```

这属于待验证性质所需的信息未进入抽象，而不只是 Guard 转换精度问题。

可以采用有限关系，避免保留完整文本和无限版本号：

```text
evidence_matches_requirements
display_matches_current_draft
feedback_matches_current_display
feedback_intent
```

例如，修改需求使证据有效性失效；生成新草稿使展示和反馈对应关系失效；展示动作完成并产生抽象反馈结果后，再按约定建立对应关系。这些变量用于检查流程是否正确清空或更新状态，不验证实际环境中的消息归属。

这些关系应有明确更新规则，不能只增加用于检查的变量而没有与实际动作一致的状态变化。

## 七、代表值校验不等于证明抽象更新覆盖完整

当前统一抽象、联合槽位和代表值验证解决了不少一致性问题，但仍需区分两项要求：

1. 同一抽象状态中的具体值，对相关判断给出一致结果。
2. 同一抽象状态中的所有具体值执行动作后，可能到达的抽象状态均被更新关系覆盖。

前者成立，不自动意味着后者成立。

`src/conversion/updates.py` 的 `list_updates()` 通过代表值执行增删，再映射回有限状态。代表值验证可以发现已覆盖样本的问题，不能独立证明任意具体列表和业务更新均得到覆盖。

建议记录每种近似的方向：

| 近似类型 | 对结果解释的影响 |
|---|---|
| 增加可能行为 | 反例可能由抽象引入，需要回查具体可行性 |
| 遗漏可能行为 | 模型通过也可能遗漏真实问题 |
| 方向不确定 | 暂不能给出一般性的性质保留保证 |

具体保证还取决于检查类型、观察映射、终止处理和公平性条件，不能把一种保证推广到所有性质。

LLM 联合抽象已有近似警告，这一做法合理；仍需进一步说明覆盖依据。通过 LLM 缩小合法成功结果时，原文引用存在也不能证明被排除的结果一定不可能发生。

## 八、失败、暂停、循环与完成需要分别解释

当前每个非空动作均增加无条件失败分支；失败跳到 transitions，并默认不产生槽位写回。这隐含了动作可能失败、失败没有部分写入等假设。

现有处理还有不同的语义边界：

- `PAUSED → Stop` 可作为本次流程暂停的抽象；需明确它是允许的停止结果，还是流程缺口，不要求当前建模环境唤醒或恢复协议。
- `ABORTED → Skip` 表达运行结束，需要业务属性继续区分失败结束与成功完成。
- 有出边的自循环可能永远执行，死锁检查无法发现这种问题。
- 对设计允许的暂停，应明确对应检查的预期，避免与意外无后继混淆。

PAT 的死锁检查排除成功终止状态；可达性证明存在一条到达路径，不能证明所有执行最终到达。[PAT 官方断言说明](https://pat.comp.nus.edu.sg/resources/OnlineHelp/htm/scr/3.1%20CSP%20Module/3.1.1.3%20Assertions.htm)

应分别定义正常完成、失败结束、允许暂停和无限循环的要求。当前活性检查针对抽象流程，例如是否存在无限重试或无进展循环，不推导真实用户必然回复或工具必然成功。若引入公平性，应说明它对抽象分支选择的约束，不能为得到通过结果而默认添加。[PAT 官方公平性说明](https://pat.comp.nus.edu.sg/resources/OnlineHelp/htm/scr/4%20Special%20Features/4.1%20Fairness.htm)

## 九、检查项生成晚于抽象，可能无法表达真正要检查的要求

`src/conversion/registry.py` 主要从 Stage 和 policy 的 Guard 收集观察条件。模型构建后，`src/conversion/checks.py` 再生成检查项。

如果“反馈表示接受”未出现在原 Guard 中，就未必进入抽象。随后即使提出“必须明确接受才能完成”，模型也可能没有足够信息表达它。

后加 observer 能记录已有事件，不能恢复从未进入模型的用户意图或版本关系。

建议先收集业务性质及其观察需求，再决定有限抽象；出现无法用现有状态表达的新性质时，应反馈到抽象阶段，或报告该性质不可验证。

此外，当前 `src/pipeline.py` 的 `PASS` 表示实际结果与各检查的 `expected` 一致。某项为 `INVALID`，只要预期也是 `INVALID`，整体仍可能 PASS。这适用于回归判断，但不能解释成控制器满足全部业务要求。

## 十、改进优先级

| 优先级 | 工作 | 目的 |
|---|---|---|
| P0 | 明确 Controller_IR 执行语义：description 的作用、出边优先级、exit 时机、动作完成含义 | 为转换确定唯一依据 |
| P0 | 处理审阅完成等关键出边的业务条件缺失 | 避免模型允许未经接受就完成 |
| P1 | 在 CSP_IR 中保留具体选择位置及选择来源 | 区分条件路由、内部决策与抽象非确定性 |
| P1 | 保留影响出边的有限动作返回类别 | 检查不同结果是否进入正确流程 |
| P1 | 按待验证要求表达证据、草稿、展示和反馈的有限有效性关系 | 检查流程清空与更新是否防止旧数据复用 |
| P1 | 让待验证性质参与抽象设计 | 避免所需信息提前被合并 |
| P2 | 记录抽象方向、更新覆盖依据及反例具体可行性 | 明确验证结论的适用范围 |
| P2 | 分开报告正常完成、失败结束、暂停、死锁和活性 | 避免不同结果混为通过或失败 |

环境请求、等待、响应、超时、取消和并发同步协议不列入当前改进优先级。

`[]` 与 `<>` 的区别是重要入口。当前需要建立的保证是：Controller_IR 中影响流程合理性的信息，能够以明确的执行约定和抽象依据保留到 PAT 检查的模型中。
