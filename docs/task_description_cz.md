PAT 加入 SPL 工作台，就是在编译链末端挂一个行为验证后端：ControllR 的 act（preconditions/effects）与 CSP# 的 [guard] event{prog} 近乎逐字同构，可确定性 lowering 成形式模型 + 自动生成的断言（死锁、checkpoint 可达、死 act 三类无需用户书写），交 PAT 跑完后，反例 trace 经现有 Trace Map 抬回到 SPL 源子句，作为 VERIFY_* 诊断进入编辑循环；工程上它落在已有 AnalyzerPack 的 backend 枚举里，Domain Pack 负责声明谓词抽象以控制状态爆炸。


给 SPL 工作台接 PAT，说白了就是在编译完成后，加一道"把规格跑一遍看"的检查。

原因是你们的 ControllR 里，每个行为本来就写成"满足什么条件才能做、做完改什么状态"——这跟 PAT 那套形式语言的写法几乎一模一样，所以能直接翻过去，不用猜。翻完之后让 PAT 穷举所有可能的执行路径，替你回答三个问题：会不会走着走着卡死没事可做？某个检查点是不是永远都过不了？有没有哪个行为的条件根本不可能满足、白写了？这三类问题不需要用户提任何要求，编译器自己就能生成检查。

一旦查出毛病，PAT 会给出一条完整的"事发经过"，再顺着你们已有的溯源表，倒推回是 SPL 规格里哪一行写出来的问题，直接变成一条报错提示给作者看。

接入位置不用新造，你们设计里那个能挂 Rego、Semgrep 的分析器接口，多加一个 PAT 就行；至于状态太多跑不动的问题，交给 Domain Pack 声明"预算只分不足/刚好/超支三档"这类简化规则来压。
