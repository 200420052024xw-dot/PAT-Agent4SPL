# Only-Guard 版本（v1）实际缺陷记录

存档日期：2026-10-30。
用途：v1 存档随附的实际缺陷记录，作为 v2（Description + Guard 联合转换）的需求依据。

本文所有行为结论来自对 v1 代码与 `inputs/Controller_IR/Internal-Comms-IR.json` 的静态核对，引用位置以本存档内代码为准；除特别注明外均未重新运行 PAT。引用的运行产物为本存档 `runs/20261010-212818-000`（manifest 为 INCOMPLETE、5 条诊断、检查数 0——它证明的是生成结构，不是检查通过记录）。

## 1. 版本定位：已实现的能力（避免误读）

v1 完整实现了以显式 Guard 为依据的转换与检测链路：

- ControllerIR → CSP_IR → CSP# 结构化转换：输入校验、统一有限抽象（含 LLM 联合抽象与代表值校验）、Guard 编译、动作结果与写回、Stage 展开为控制位置。
- 失败缺口检查与有依据的补全（terminate / pause / edge / retry），未解决的保留 `FAILURE_GAP` 警告。
- AI 检查项生成（代码校验）、PAT 逐项执行、来源追溯（source_map / render_map / failure_records）。

必须区分两个结论（引自组会汇报 §1）：

- **转换基础已实现**：能建立有限模型、生成 CSP#、支持模型检查。
- **业务语义覆盖仍需完善**：仅依据显式 Guard，不保证保留 description 中的全部决策要求。

本文记录的是后一类问题。检测只报告问题和反例、不自动修复，且验证范围限于流程设计合理性、不含环境交互——这些是 v1 的既定边界，不算缺陷。

## 2. 核心缺陷：Only-Guard

**原有出边的分支条件直接来自显式 Guard；transition 的 description 完全不参与条件编译，且没有任何诊断提示"说明中的业务约束未被覆盖"。**

代码证据（本存档 `src/conversion/compiler.py`）：

- `_compile_outgoing()`（约 122 行起）只把 `item.get("guard", True)` 交给 `compile_guard`，`item["description"]` 从未被读取。
- 对比：Stage / 动作的 description 会进入 `resolve_failure`、`resolve_effects` 的上下文（`_compile_step`，约 234 行起），唯独决定流程走向的 transition description 被丢弃。
- 后果：转换"成功"与语义"保留"在产物和诊断中无法区分——**静默丢失**。

## 3. 已核实的行为缺陷（真实输入）

### 缺陷 3.1：未经用户接受也允许完成

`/stages/present_and_review/transitions/0` → completed：

| 对比项 | 表达的条件 |
|---|---|
| description | 用户明确接受当前展示版本，且没有同时要求修改或提问 |
| 显式 Guard | doActivity 成功 ∧ draft != "" |

情境：已展示非空草稿，PRESENT 成功，用户回复"第二段请改一下，先不要定稿"。Guard 两个条件均为真，完成出边仍可执行。模型**允许**过早完成（是允许，不是必然选择）。

加重因素：`review_feedback` 在全部 Guard 中只被判断是否为空，抽象仅有 EMPTY / NONEMPTY——"接受 / 修改 / 提问"的意图维度从未进入模型。该约束即使想补也没有承载状态（见 §4.1）。

### 缺陷 3.2：三条 `guard: true` 丢失分支适用情境

`/stages/present_and_review/transitions/3~5` → revise_slot / ask_clarification / explanation：

| 目标阶段 | description 表达的业务前提 | Guard |
|---|---|---|
| revise_slot | 用户明确修改需求或检索条件，先更新槽位 | true |
| ask_clarification | 反馈含糊，无法判断接受还是修改，或修改内容存在歧义 | true |
| explanation | 用户提出需要说明的概念、用途或草稿内容问题 | true |

Guard 全为 true，三条出边无条件同时可选。用户只问"3P 是什么意思"时，模型仍允许选择修改需求分支。**问题不是缺分支，而是模型不知道各分支何时适用**，分支选择退化为纯非确定。

### 缺陷 3.3：自循环条件过宽，且死锁检查不可见

`/stages/revise_slot/transitions/0` → revise_slot（自循环）：

- description："同一回复还有尚未应用的明确值；已完成的相对修改不得重复。"
- Guard 只检查 doActivity 成功。全部修改已应用后，自循环仍被启用。

所需"剩余修改 / 已处理"历史信息在当前有限状态（槽位当前值 + 执行状态）中无法表达。且有出边的无限循环不属于死锁，PAT 死锁检查发现不了（见 §5）。

### 缺陷 3.4：动作结果约束同样丢失

`/stages/generate_3p` description 要求"始终输出全文"（完整草稿），但 v1 产物（本存档 `runs/20261010-212818-000/model.csp` 第 254 行附近）中 doActivity 成功边仍展开 `DRAFT_EMPTY` 与 `DRAFT_NONEMPTY` 两条（generate_newsletter、revise_3p 等同样如此）。

说明 description 不仅可能约束 transition，还可能约束动作成功结果；`resolve_effects` 只在原文"明确限制结果"时缩小合法值，未覆盖此类要求。

## 4. 结构性根因（为什么不能事后补救）

### 4.1 抽象由 Guard 收集驱动，语义需求来得很晚

`registry.py` 只从 Stage / policy 的 Guard 收集判断 → 有限抽象只区分 Guard 需要区分的信息 → `checks.py` 的检查项生成在抽象之后，且被明确禁止引入有限域无法区分的新条件；后加 observer 也只能记录已有事件，无法恢复从未进入模型的意图。

**语义需求必须先于抽象收集**——这是 v2 流程顺序的根本依据（组会汇报 §5.2）。

### 4.2 历史与版本关系无法表达

IR 要求"修改需求后不得沿用旧证据""新草稿不能复用旧确认""接受必须针对刚刚展示的版本"。新旧草稿均抽象为 NONEMPTY、新旧反馈均抽象为 NONEMPTY 时，`旧草稿+旧确认 / 新草稿+旧确认` 无法区分。需要 `evidence_matches_requirements`、`feedback_matches_current_display` 一类有限关系变量及与动作一致的更新规则。缺陷 3.3 的"剩余修改"同属历史信息缺口。

### 4.3 选择语义未区分

renderer 把同一控制位置的所有出边统一用 `[]` 连接，混同了含义不同的选择：动作成功 / 失败、黑盒动作的非确定返回、多 Guard 同时成立的路由、policy 结果。无业务优先级表达。PAT 3.5 区分 `[]` / `[*]` / `<>`，是否需要区分取决于执行约定（v2 待确认项）。

### 4.4 Stage 生命周期顺序缺少执行契约

`_next()` 固定 entry → doActivity → exit → policy → transitions，即先执行 exit 再判断迁移。若 Controller_IR 的语义是"确定迁移后才退出当前状态"，则无可用迁移时 exit 已产生副作用、exit 的写回可能改变本次出边可用性。自循环是否重新执行 entry、失败是否执行 exit、policy 触发位置与多个 policy 的先后，均无明确约定。

## 5. 验证与解释边界（结论强度限制）

- **PASS 语义**：只表示实际结果与各检查的 expected 一致（某项 INVALID 但预期也是 INVALID 仍算整体 PASS），适合回归判断，不能解释为"控制器满足全部业务要求"。
- **可达性 ≠ 必然到达**；死锁检查排除成功终止，发现不了有出边的活循环（与 3.3 相关）。
- **抽象近似无方向记录**：代表值经 OPA 复核只能发现已知组合的不一致，不能证明未知业务条件在无限原空间上的完备性；`updates.py` 的代表值增删同样只是采样。增加行为 → 反例可能由抽象引入（假阳性）；遗漏行为 → 通过可能漏掉真实问题（假阴性）。近似方向未系统记录。
- **约定性搁置**：`guard: true` 与失败描述的冲突不做分析；`FAILURE_GAP` 仅警告、不阻止输出，不能解释为失败处理已完整。

## 6. 问题归属（三层）

| 层 | 问题 | v2 对应要求 |
|---|---|---|
| IR 层 | 关键决策依据只存在于自然语言 description，无结构化条件 | 提取结果需带原文与输入路径依据；无法结构化的显式报告 |
| 转换层 | description 业务约束被静默丢弃，无诊断 | 未覆盖的约束必须有诊断（不再静默） |
| 验证依据层 | 未声明抽象保留哪些性质，结论强度不明 | 近似方向与覆盖依据写入诊断 |

## 7. v2 必须满足的要求（源自以上缺陷）

- **R1 语义提取先于抽象**：从 transition（及关联 Stage / 动作 / policy）的 description 提取影响行为的业务条件，结构化、带原文与输入路径；提取结果参与抽象设计。
- **R2 意图维度进入有限抽象**：如 `feedback_intent ∈ {accept, modify, question, ambiguous}`，作为 PRESENT 类动作的有限返回类别（语义缺口文档 §四：仅保留 success 过粗）。
- **R3 有效出边条件 = 原 Guard ∧ 提取条件**（约定待确认：冲突时报告而非自动合并）。
- **R4 歧义与冲突显式报告**：多意图组合、description 与 Guard 冲突、无法结构化的说明，均可见。
- **R5 历史与版本关系的有限表达**（剩余修改、证据 / 反馈对应关系），配套与动作一致的更新规则。
- **R6 第一轮以 present_and_review 为验证对象**：仅动作成功不得直接导致完成；修改或提问时不得进入完成（组会汇报 §5.4 验收重点）。
- **R7 转换层不静默**：description 中未被覆盖的业务约束在 diagnostics 中可见，"转换成功"不再与"语义保留"混同。
